# 业务逻辑文档规范

## 核心规则

每当完成一段业务逻辑的编写或修改后，**必须**在项目根目录的 `docs/` 文件夹中记录本次更新。如果 `docs/` 不存在，先创建。

## 文档组织

按业务模块分文件，一个业务领域一个文档：

```
docs/
├── auth.md           # 认证相关
├── prayer.md         # 祷告相关
├── relationships.md  # 关系管理
├── payment.md        # 支付相关
└── ...
```

- 如果对应的业务文档已存在 → 在文件中追加更新记录
- 如果不存在 → 创建新文件

## 文档格式

每个业务文档的结构：

```md
# [业务模块名]

## [功能名称]

- **更新日期**：YYYY-MM-DD
- **涉及文件**：
  - `path/to/file1.tsx` — 简要说明
  - `path/to/file2.ts` — 简要说明
- **业务逻辑**：
  [用简洁的语言描述这段逻辑做了什么、为什么这样做、关键的业务规则是什么]
- **注意事项**（可选）：
  [特殊边界情况、依赖关系、后续需要注意的点]
```

### 示例

```md
# 认证

## 验证码登录流程

- **更新日期**：2026-02-05
- **涉及文件**：
  - `components/AuthModal.tsx` — 登录弹窗 UI 和流程控制
  - `lib/api/verification.ts` — 验证码发送和校验 API
  - `app/api/auth/verify-code/route.ts` — 验证码校验接口
- **业务逻辑**：
  用户输入邮箱或手机号后，系统自动识别类型并发送对应验证码。验证通过后，检查用户是否已注册：已注册则直接登录，未注册则跳转信息完善页面。验证码有效期 5 分钟，同一联系方式 60 秒内不可重复发送。
- **注意事项**：
  Google OAuth 登录走不同流程，但最终都进入同一个信息完善页面。
```

## 写作原则

- **记录业务逻辑，不是代码实现** — 重点说明"做了什么"和"为什么"，不要贴大段代码
- **保持简洁** — 每条记录控制在几行内，不写长篇大论
- **追加而非覆盖** — 同一模块的新逻辑追加到文档末尾，保留历史记录
- **只记有意义的业务逻辑** — 纯样式调整、简单 bug 修复不需要记录
